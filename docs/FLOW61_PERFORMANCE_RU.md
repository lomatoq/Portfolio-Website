# FLOW61 — мобильная производительность без снижения качества

Исходная версия: `1fe9102` (FLOW60). Задача: устранить лишнюю работу при мобильной прокрутке, сохранить материалы, свет, размытия, разрешение, сглаживание и desktop-навигацию.

## Причины и изменения

Подтверждённая проблема CPU: цикл подсветки карьерных карточек читал `window.scrollY` между записями CSS. Браузер был вынужден синхронно пересчитывать стили несколько раз за кадр. Теперь координаты снимаются один раз, размеры неизменяемых контейнеров читаются до анимационных записей. Такой же снимок координат применяется в intro и экспериментальных эффектах. Геометрия самого стекла по-прежнему берётся после перемещения карточек, чтобы совпадать с DOM.

На touch-устройствах больше не строится невидимый SVG-контур мышиного курсора. Его состояние продолжает обновляться; внешний вид и работа курсора с мышью сохраняются.

Статическая конфигурация вершин WebGL сохраняется в VAO вместо повторной настройки каждый кадр. Есть путь WebGL 1 без расширения VAO. При освобождении рендера VAO также удаляются.

Повторный resize с теми же размерами, DPR и качеством больше не удаляет и не создаёт заново framebuffer/texture. Лимиты GPU читаются один раз при создании контекста. Настоящее изменение размеров, в том числе поворот телефона, по-прежнему пересоздаёт буферы с прежним разрешением.

Проверка шейдеров выявила `pow(x, 2.)` с отрицательным x. Для GLSL такой результат не определён; используется `pow(abs(x), 2.)` — та же математическая функция, без зависимости от драйвера. Коэффициенты света, число выборок размытия, детали травы и MSAA не изменены. См. [спецификацию GLSL ES](https://www.khronos.org/files/opengles_shading_language.pdf) и [рекомендации WebGL по синхронным запросам GPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices).

## Измерения

Chrome, мобильная эмуляция, DPR 2, full quality, сцена Playgendary. По 120 кадров, одинаковые viewport и позиция, исходная и новая версии последовательно. Измеряется сумма CPU-времени основных модулей `tick/read`, а не полное время GPU или FPS телефона.

| Viewport | Среднее CPU до / после | Медиана до / после | p95 до / после |
|---|---|---|---|
| 390 × 844 | 5,61 / 2,68 мс | 5,10 / 2,10 мс | 8,00 / 5,30 мс |
| 844 × 390 | 5,35 / 2,35 мс | 4,80 / 1,90 мс | 7,80 / 4,10 мс |
| 1440 × 900 | 5,22 / 3,33 мс | 4,70 / 2,60 мс | 7,30 / 7,00 мс |

За 120 кадров вызовы `vertexAttribPointer`: 1320 → 0 после прогрева. Серия из 12 resize без изменения размеров: 24 выделения texture → 0; 36 запросов GPU limits → 0. Render size и 2× MSAA совпадают до/после: 546×1181, 1181×546, 1959×1224 соответственно. Это проверяемое устранение работы, не переключение в eco.

## Проверки и границы вывода

- `tests/performance61.cjs`: сравнение CPU, счётчики WebGL, отсутствие повторных аллокаций, поворот viewport.
- `tests/touch60.cjs`: настоящие touch-события Chrome через CDP, монотонный вертикальный swipe, горизонтальная галерея, resize, вложенные попапы и возврат к прокрутке.
- `tests/flow59.cjs`: wheel, контрольные позиции, первая карточка, смена направления, стеклянные попапы и Escape.
- `tests/render61.cjs`: WebGL 2, WebGL 1 с VAO и без него, WebKit; главы, поворот и попап.
- `tests/visual61.cjs` и `tests/compare61.py`: контрольные кадры сравниваются с FLOW60 при одинаковом времени анимации, позиции и состоянии видео. Внешние шрифты отключены одинаково для обеих версий; обработка IntersectionObserver завершается до снимка.

Все перечисленные проверки пройдены. Визуальная матрица: четыре позиции × три viewport (390×844, 844×390, 1440×844), всего 12 пар. 11 пар совпали побитно; в одной максимальная разница канала составила 1/255, средняя — 0,00000027 из 255. Положение страницы проверяется перед каждым кадром; загрузчик должен полностью завершиться. Это проверка контрольных состояний, а не доказательство совпадения каждого кадра на всех GPU.

На пользовательской записи заметны рывки и сильные засветки. Рывки согласуются с измеренной лишней CPU-работой. Ошибка `pow` — подтверждённый дефект переносимости, но считать её доказанной причиной всех засветок именно на iPhone нельзя без профиля этого устройства.

Вердикт: **PROMOTE** для устранения подтверждённой лишней работы с сохранением full quality. Производительность физического iPhone и всех состояний Safari не измерена; эмуляция и WebKit на Windows не дают гарантии постоянных 60 FPS на телефоне.

## Повторение

Запустить статический сервер, установить Playwright для тестов и Chrome. Для A/B сохранить `index.html` из коммита `1fe9102` во внешний файл и указать его через `BASELINE_HTML`.

```powershell
$env:FLOW59_URL = 'http://127.0.0.1:4192/'
$env:BASELINE_HTML = 'C:/path/to/flow60.html'
node tests/performance61.cjs
node tests/touch60.cjs
node tests/flow59.cjs
node tests/render61.cjs
node tests/visual61.cjs
python tests/compare61.py flow61-visual
```
